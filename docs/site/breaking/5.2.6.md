# Breaking changes — hasta **5.2.6**

Salto: **5.1.1 → 5.2.6**. La serie 5.2 es una sola guía: acá está todo lo que cambió respecto de
**5.1.1** y **qué hacer** en cada caso. Si generás el CSS desde `comegen.config.json` o desde el
Theme Builder, los puntos 1 a 3 ya vienen resueltos; si definís los tokens **a mano**, empezá por
ahí.

## 1. Las variantes usan tokens nuevos

Cada color necesita ahora:

- `--cu-color-{color}-solid-text` — texto de `solid` y `none` (el polo negro/blanco de máximo
  contraste contra el relleno y sus estados).
- `--cu-color-{color}-text-on-ghost` — texto sobre el tinte `ghost` (hasta 20 %).
- `--cu-color-{color}-text-on-soft` — texto sobre el tinte `soft` (hasta 35 %).
- `--cu-color-{color}-text-on-subtle` — texto sobre el tinte `subtle` (hasta 30 %).

**Si no los definís**: esas variantes no se rompen, pero el texto cae al color heredado (pierde el
contraste calculado). `solid` ya no usa blanco fijo sobre el color: usa `-solid-text`.

```css
:root {
  --cu-color-primary: #0f62fe;
  --cu-color-primary-solid: #0f62fe;       /* mismo base: ya no se oscurece */
  --cu-color-primary-solid-text: #ffffff;  /* negro o blanco, el de más contraste */
  --cu-color-primary-text: #0f62fe;        /* sólo se mide contra surface */
  --cu-color-primary-text-on-ghost: #0b4fc4;
  --cu-color-primary-text-on-soft: #0a469f;
  --cu-color-primary-text-on-subtle: #083a80;
}
```

**Qué hacer**: agregá los cuatro tokens para los seis colores que uses (o regenerá el CSS desde la
config, que ya los emite). El generador los deriva con el piso de contraste; si los escribís a mano,
elegí el polo de texto y los tonos que midan ≥ 4.5:1 contra el relleno o el tinte.

## 2. `-solid` conserva el color del tema y `-text` cambia de base de medición

- `--cu-color-{color}-solid` (y sus estados `-solid-hover` / `-solid-active`) es el **color base del
  tema tal cual**. Antes el generador lo oscurecía o aclaraba para forzar contraste con blanco; ahora
  el contraste lo resuelve el **texto** (`-solid-text`). Visualmente, los rellenos `solid` de los
  temas oscuros se ven más brillantes/saturados que antes.
- `--cu-color-{color}-text` se mide **sólo contra `--cu-color-surface`** (casos `ghost`, `outlined` y
  `link`). Para fondos tintados (`ghost`/`soft`/`subtle`) usá `-text-on-ghost`, `-text-on-soft` y
  `-text-on-subtle`; el `-text` anterior ya no está garantizado sobre el tinte.
- Cuando el relleno `solid` queda a menos de 3:1 de la superficie, los componentes dibujan el borde
  `--cu-color-{color}-border` para delimitar el control.

**Qué hacer**: si pintás texto propio sobre un fondo `solid`, usá `-solid-text` en vez de
`white`/`black`; si lo pintás sobre un tinte (`ghost`/`soft`/`subtle`), usá el `-text-on-*` que
corresponde. Revisá cualquier CSS tuyo que asumiera que `-solid` era un tono ajustado por el
generador: ahora es el base exacto del tema.

> Mirá también [Configuración](/configuracion#tokens-css) y
> [Personalización](/personalizacion) para el detalle de los tokens.

## 3. El CSS exportado por el Theme Builder aplica sin `data-theme`

`generateThemeCSS` emite `:root` (el tema activo, sin atributo) además de `[data-theme="…"]` (para
cambiar de tema). Si comparabas el CSS exportado esperando sólo el selector `[data-theme]`, ahora
trae los dos.

**Qué hacer**: nada: es aditivo. Si tenías un `data-theme` en `<html>` para forzar el tema, podés
dejarlo (sigue ganando) o quitarlo; el `:root` ya trae el tema activo.

## 4. `cu-side-over`: `open()` pasa a llamarse `show()`

En 5.2.0 el método `open()` se renombró a **`show()`**. `open()` nunca funcionó: la prop booleana
`open` define `el.open` en el custom element y tapaba al método (`t.open is not a function`). `open`
sigue siendo el atributo/prop booleano (mismo patrón que `<dialog>`); el método que abre el panel es
`show()`.

Además, en el custom element el panel se renderiza dentro de su shadow root (teleport desactivado)
para que el slot del host se proyecte; antes se teleportaba al `body` y el contenido quedaba vacío.
En Vue el teleport a `body` sigue siendo el default y la prop `teleport` permite controlarlo.

**Qué hacer**: reemplazá `el.open()` por `el.show()` (y `close()` / `toggle()` siguen igual). Si
buscabas el panel en `document.body` con el custom element, buscalo en el shadow root del host.

## 5. `cu-autocomplete`: elegir una sugerencia ya no cierra el panel

Desde 5.2.1, al elegir una sugerencia el panel **no se cierra**: resetea el filtrado y muestra todos
los items con el elegido checkeado; al volver a escribir, el filtrado se reanuda con la cadena
actual. Click afuera sigue cerrando y `minChars` se respeta igual.

**Qué hacer**: si dependías del cierre automático, cerralo desde el handler de `select` con el
método `close()` del componente (`autocomplete.close()` en el custom element). Si querías el cierre
al elegir, ese es el único cambio necesario.

## 6. `cu-number-input`: el texto se respeta al tipear y se confirma con `Enter`/`blur`

En 5.2.3 cambió el camino de escritura. Antes `onInput` clampeaba y **reescribía el texto en cada
tecla**: con `min="1950"`, tipear `2` (camino a `2019`) lo convertía en `1950` y el campo quedaba
inservible. Ahora:

- El texto se respeta tal cual mientras se escribe.
- `update:modelValue` se emite **sólo** cuando el número parseado cae dentro de `[min, max]`; un
  campo vacío limpia el modelo; un texto no numérico no toca el modelo (sigue el último válido).
- `Enter` o `blur` recortan el texto al límite más cercano y emiten `change` una sola vez.
- `set`/`increment`/`decrement` siguen clampeando y el botón del límite sigue deshabilitado.

**Riesgo de UX (a propósito)**: el campo puede quedar con texto fuera de rango hasta confirmar, y el
`v-model` refleja el **último valor válido**, no lo tipeado; `get()` en ese estado devuelve ese
último válido. Es el tradeoff necesario para poder tipear `2019` con `min="1950"`.

**Qué hacer**: si validabas en cada `update:modelValue`, agregá la validación también en `change`
(ahí llega el valor confirmado y recortado). No dependas de que `get()` devuelva el texto visible
mientras el campo está en edición.

## 7. `cu-table`: `Escape` cancela la edición

Al cancelar, el editor se desmontaba y el `blur` que despacha el navegador disparaba `saveEdit`: se
emitía `edit-save` con lo tipeado, aunque la ficha decía que cancelaba. Desde 5.2.3 `Escape` cancela
de verdad: emite `edit-cancel` y el valor de la fila no cambia.

**Qué hacer**: si escuchabas `edit-save` esperando también el cierre por `Escape`, escuchá
`edit-cancel` para descartar. Nada que migrar si sólo guardabas por `Enter`/blur.

## 8. `cu-command-palette`: `label`, `description` e `icon` se muestran como texto

El `icon` se interpolaba como HTML (la ficha lo afirmaba); desde 5.2.3 se interpola y el marcado se
escapa. `label` y `description` también se muestran como texto.

**Qué hacer**: pasá un emoji o un glifo corto en `icon`. Si necesitabas un `<svg>`, va como texto
escapado: movelo a un slot/contenido propio o reemplazalo por un ícono de texto. Revisá también
`label`/`description` si les pasabas HTML.

## 9. `cu-button`: link `disabled`/`loading` no navega, y el modo link es un único `<a>`

Cambios de 5.2.3 en el modo link y en los estados:

- Un link `disabled`/`loading` **ya no navega**: pierde `href`, expone `aria-disabled`, sale del tab
  order (`tabindex="-1"`) y cancela el click (tampoco burbujea a listeners externos).
- `to` con esquema ejecutable (`javascript:`, `data:`, `vbscript:`, incluso ofuscado) no se renderiza
  como link; un `color` inválido cae a `neutral` y un `type` inválido a `button` (el default HTML de
  un valor inválido sería `submit`).
- `target="_blank"` agrega `rel="noopener noreferrer"`.
- Con `to`, el componente renderiza **un único `<a>`** con las mismas clases, slot y estados que el
  botón (antes era `<a><button>…</button></a>`). Sin `to` sigue siendo `<button>` y `type` aplica.

**Qué hacer**: si usabas un link deshabilitado como “place-holder navegable”, ahora no hace nada:
mostralo como texto, o quitá `disabled` si debe navegar. Revisá selectores CSS y handlers que
asumían `a > button` o el doble nodo; y validá `type`/`color`/`to` que vengan de datos.

## 10. `cu-checkbox` y `cu-switch`: `change` emite `boolean`

Antes la interacción reenviaba el `Event` nativo y `set()`/`reset()` emitían
`{ target: { checked } }`; desde 5.2.3 los tres caminos emiten el **valor nuevo** (`boolean`), igual
que `update:modelValue`. En el custom element el payload también llega como `boolean`.

**Qué hacer**: cambiá `e.target.checked` / `e.detail.target.checked` por `e.detail` (o
`update:modelValue`). Si tenías código puente para normalizar el payload, borralo.

## 11. Los atributos de los custom elements se castean por tipo

El bridge de atributos pasaba el string crudo a la prop: `disabled="false"` era truthy y apagaba el
control, y `model-value="false"` dejaba el checkbox marcado. Desde 5.2.3 cada atributo se castea con
los tipos declarados de su prop: un Boolean presente es `true` (`""` y `"true"`), el texto explícito
`"false"` es `false`, y Number se parsea. Aplica a **todos** los custom elements; sin tipos
declarados el valor queda string. Además, los atributos del host que no son props ya no se
camelizan (`aria-describedby`, `aria-labelledby`, `data-testid` llegan con su nombre original).

**Qué hacer**: quitá los `disabled="false"` y los `"false"` textuales que se usaban como truthy;
para apagar un booleano, omití el atributo. Si leías `get()` esperando el string `"false"`, ahora
devuelve `false` (boolean). Revisá selectores `[ariadescribedby]`-style: el nombre ya es el exacto.

## 12. Otros cambios visibles en 5.2.x

| Componente | Cambio | Qué hacer |
|---|---|---|
| `cu-card` (custom element) | El wrapper ya no re-emite el click de su contenido como `CustomEvent`: el evento nativo llega una sola vez al host (antes un listener veía dos). | Quitá el dedupe/doble guard que compensaba el evento duplicado. |
| `cu-cells-importer` | El atributo `readonly` pasa a `read-only` (con `readonly` el valor no llegaba al prop). | Renombrá el atributo en el HTML. |
| `cu-floating-button` | `z-index` baja de 1000 a **900**: el FAB queda por debajo de `Modal` (1000) y `SideOver` (1100). | Si lo subías con CSS, ajustá el valor contra la nueva capa. |
| `cu-alert` | `role` por urgencia: `warning`/`danger` son `alert` (`assertive`); `primary`, `secondary`, `neutral` y `success` son `status` (`polite`). | Si necesitabas interrumpir siempre, usá `warning`/`danger`; si anunciabas un aviso informativo, ahora espera turno. |
| `cu-tabs` | Un `modelValue` que apunta a una tab `disabled` cae en la primera habilitada; un `color` inválido cae a `primary`; click en la tab activa ya no emite `change`. | No apuntes `v-model` a tabs deshabilitadas; validá `color`; no esperes `change` por re-click. |
| `cu-pagination` | `currentPage` fuera de rango se clampa al renderizar (la prop no se modifica sola) y la lista vive en un `<nav aria-label="Paginación">`. | Leé la página efectiva desde el render/eventos, y ajustá selectores que asumían el `div` raíz. |
| `cu-table` | Una celda `string[]` renderiza **una línea por elemento** (antes se veía el JSON serializado); `items-per-page` inválido cae al default `10`. | Quitá workarounds de `JSON.stringify` y formateá el array como querés verlo. |
| `cu-number-input` / `cu-color-picker` | `set`/`get`/`increment` son inmediatos: no esperan al próximo tick del host. | Si leías `get()` en el tick siguiente esperando el valor viejo, ahora obtenés el nuevo (comportamiento correcto). |
| Bordes y foco | Los tokens `--cu-border-color*` se derivan con piso de contraste (≥ 3:1): separadores, bordes de card y contornos quedan más marcados, sobre todo en temas claros. | Es intencional (WCAG 1.4.11); si querés bordes más suaves, pisá el token. |
